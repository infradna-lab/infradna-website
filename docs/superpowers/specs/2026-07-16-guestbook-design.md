# 학회 부스용 임시 방명록 — 설계

- 작성일: 2026-07-16
- 상태: 설계 확정, 구현 대기
- 수명: 학회 부스 운영 기간 한정. 종료 후 **롤백 전제**.

---

## 1. 배경과 목적

**IAHR-APD2026 · SWGIC2026** 부스 운영 중 방문객이 QR로 사이트에 들어와 짧은
메시지를 남기고, 그 목록을 공개적으로 볼 수 있게 한다. 부스 방문의 흔적을 남기는
참여 요소가 목적이며, 방문자 수 집계는 이미 Vercel Analytics가 담당하므로 이
기능의 목표가 아니다.

두 학회는 **동시 개최**이므로 방명록을 학회별로 나누지 않고 **하나로 통합**한다.
(근거는 2절)

**이것은 사이트의 방향 전환이 아니다.** 현재 사이트는 정적 브로슈어이며 그 성격을
유지한다. 방명록은 기간 한정 이벤트 도구로 취급하고, 그렇게 취급하는 것이
설계 전반의 제1원칙이다.

### 비목표 (명시적으로 하지 않는 것)

- 개인정보 수집 — 이름·연락처·소속을 묻지 않는다
- 상시 커뮤니티 기능 — 답글, 좋아요, 신고 없음
- 실시간 갱신 — 부스 모니터에 흘려보내는 용도가 아니다
- 사이트 네비게이션 노출 — 진입은 QR로만 안내한다
- 관리자 화면 — 3일짜리 기능에 CRUD 콘솔을 만들지 않는다

## 2. 핵심 결정과 근거

| 결정 | 근거 |
|---|---|
| Upstash Redis + Vercel Function | 리스트 키 하나로 충분해 스키마·마이그레이션이 없고, Marketplace로 붙였다 떼기 쉽다. Supabase는 anon 키 노출과 RLS 설계 부담이 3일짜리 기능에 과하고, 외부 SaaS 임베드는 "개인정보 통제권을 우리가 쥔다"는 전제와 모순된다. |
| 키에 TTL 설정 | "개인정보를 보관하지 않는다"를 약속이 아니라 인프라가 보장하는 사실로 만든다. 롤백 시 지울 데이터가 남지 않는다. |
| 읽기 공개 / 쓰기 키 게이팅 | 공개 URL은 부스 밖에서도 접근된다. 부스 방문객 경험(QR→폼)은 그대로 두면서 무작위 쓰기를 차단한다. 3일 기준 봇 유입 확률은 낮지만, 부스 화면에 욕설이 뜨는 비용이 확률 대비 크다. |
| IP·User-Agent 미저장 | 익명이 전제이므로 식별 흔적을 남길 이유가 없다. 키 게이팅을 택해 IP 기반 rate limit이 불필요해졌기에 가능한 선택이다. |
| `src/guestbook/` 단일 폴더 격리 | 롤백이 전제다. 기존 파일에 스며들면 되돌리기가 "흔적 찾아 지우기"가 된다. |
| 두 학회 통합 방명록 (분리하지 않음) | 동시 개최이므로 학회를 나눌 실익이 없다. 만료 시각이 하나로 충분하고(먼저 끝난 학회의 글이 남는 문제가 없다), 키 없이 들어온 방문자에게 어느 목록을 보여줄지 정할 필요도 없다. |

## 3. 구조

기존 파일 중 수정하는 것은 **`src/App.tsx` 하나뿐**이며, 여기서도 import 1줄과
Route 1줄만 추가한다. `HomePage`, `FooterSection`, 네비게이션은 건드리지 않는다.

```
api/guestbook.ts              (신규) Vercel Function — GET/POST
src/guestbook/                (신규) 이 폴더가 곧 기능의 경계
  GuestbookPage.tsx             라우트 진입점, 데이터 로딩·상태 소유
  GuestbookForm.tsx             입력 폼 — 쓰기 키가 있을 때만 렌더
  GuestbookList.tsx             메시지 카드 목록
src/App.tsx                   (수정) `/guestbook` 라우트 추가
```

### 컴포넌트 경계

- **GuestbookPage** — URL에서 `k` 파라미터를 읽고, 목록을 불러오고, 로딩·에러
  상태를 소유한다. 자식에게 데이터와 콜백을 내려준다.
- **GuestbookForm** — 입력값과 제출 상태만 안다. 제출은 props로 받은 콜백에 위임하며
  fetch를 직접 하지 않는다.
- **GuestbookList** — 항목 배열을 받아 렌더만 한다. 상태 없음.

## 4. 데이터

Upstash Redis 리스트 키 하나를 쓴다.

- **키**: `guestbook:2026`
- **쓰기**: `LPUSH` (최신이 앞)
- **읽기**: `LRANGE 0 -1`
- **상한**: 쓰기마다 `LTRIM 0 499` — 최근 500개만 유지
- **만료**: 쓰기마다 `EXPIREAT`을 환경변수 `GUESTBOOK_EXPIRES_AT`(ISO 8601) 기준
  절대 시각으로 설정. 슬라이딩이 아닌 고정 만료이므로 마지막 글이 언제 올라오든
  예정된 시각에 전체가 소멸한다.

### 항목 스키마 (JSON 문자열로 저장)

```ts
{
  id: string        // crypto.randomUUID()
  nickname: string  // 최대 12자. 빈 값이면 "익명 방문자"로 서버가 대체
  message: string   // 1~100자, 필수
  createdAt: string // ISO 8601, 서버가 생성
}
```

IP, User-Agent, 세션 식별자는 **저장하지 않는다**.

## 5. API

### `GET /api/guestbook`

인증 없음. `200 { entries: Entry[] }` (최신순). 목록이 비면 빈 배열.

### `POST /api/guestbook`

요청 본문:

```ts
{ key: string, nickname?: string, message: string }
```

서버는 순서대로 검증한다:

1. `key !== process.env.GUESTBOOK_WRITE_KEY` → `403 { error: "INVALID_KEY" }`
2. `message`가 비었거나 100자 초과, `nickname`이 12자 초과 → `400 { error: "INVALID_INPUT" }`
3. 개인정보 패턴 검출 (6절) → `400 { error: "PII_DETECTED" }`
4. 통과 → `LPUSH` → `LTRIM` → `EXPIREAT` → `201 { entry: Entry }`

서버는 기계가 읽는 코드만 반환하고, **한국어 문구는 클라이언트가 매핑**한다.
서버 응답 문자열을 그대로 화면에 뿌리지 않는다.

### 환경변수

| 이름 | 출처 | 용도 |
|---|---|---|
| `GUESTBOOK_WRITE_KEY` | 수동 등록 | 쓰기 게이팅. 코드에 박지 않아 유출 시 값만 교체·재배포 |
| `GUESTBOOK_EXPIRES_AT` | 수동 등록 | 데이터 절대 만료 시각 (ISO 8601) |
| `UPSTASH_REDIS_REST_URL` | Marketplace 자동 주입 | Redis 접속 |
| `UPSTASH_REDIS_REST_TOKEN` | Marketplace 자동 주입 | Redis 접속 |

## 6. 쓰기 제한과 개인정보

### 두 겹 게이팅

QR에 `/guestbook?k=<키>` 형태로 키를 심는다.

- **프론트** — `k` 값이 있으면 폼을 렌더, 없으면 목록만. 이것은 **경험 분기일 뿐
  방어가 아니다.**
- **서버** — POST에 담겨 온 키를 `GUESTBOOK_WRITE_KEY`와 대조. **이것이 실제 방어다.**
  프론트 게이팅만으로는 `/api/guestbook`에 직접 POST하는 것을 막지 못한다.

### 개인정보 차단

익명이어도 방문객이 자유 텍스트에 스스로 연락처를 적을 수 있다. 서버에서
다음 패턴을 검출해 저장을 거부한다.

- 전화번호: `/01[0-9][-.\s]?\d{3,4}[-.\s]?\d{4}/`
- 이메일: `/[\w.+-]+@[\w-]+\.[\w.]+/`

폼에도 "연락처는 남기지 말아주세요" 안내를 미리 노출하고, 거부 시 같은 취지의
문구를 보여준다.

**의도적 한계**: "공대 김씨"처럼 패턴에 걸리지 않는 자기 식별은 통과한다. 3일짜리
부스 방명록에 이름 검출을 붙이는 것은 과잉이며, 실질 위험(연락처가 공개 페이지에
박제되는 것)은 위 두 패턴으로 대부분 차단된다. 100자 제한도 여기에 기여한다.

## 7. 화면

QR 진입이므로 **휴대폰 세로 화면이 기본**이다. 데스크톱은 가운데 정렬로 최대 폭만
제한한다.

구성: 네이비 헤더 → (키 있을 때) 폼 → 메시지 카드 목록.

헤더 문구는 큰 제목 **"방명록"**, 그 아래 학회명 **"IAHR-APD2026 · SWGIC2026"**.
두 학회가 동시 개최이므로 병기하며, 방문객이 어느 부스에서 왔든 같은 화면을 본다.

기존 사이트 컨벤션을 따른다.

- 브랜드 색: 네이비 `#1e3a5f`, 시안 `#0891b2` (임의값 유틸리티)
- 한글은 `break-keep`
- 애니메이션은 `'framer-motion'`에서 import (`motion/react` 아님)
- Tailwind는 기본 유틸 + `slate-*` 중립 팔레트

폼에는 메시지 글자수 카운터(`0/100`)를 둔다.

## 8. 에러 처리

부스에서 가장 치명적인 실패는 **입력한 글이 날아가는 것**이다. 방문객은 다시
타이핑하지 않고 떠난다.

- **제출 실패** — 입력 텍스트를 유지한 채 에러 문구만 표시. 폼을 초기화하지 않는다.
- **제출 중** — 버튼을 잠가 중복 등록을 막는다.
- **목록 로딩 실패** — "목록을 불러올 수 없습니다 + 다시 시도" 표시. 폼은 살려둔다.
- **제출 성공** — 목록을 다시 불러온다. 낙관적 업데이트는 하지 않는다(부스 규모에서
  체감 차이가 없고 실패 시 롤백 처리만 늘어난다).

검증은 클라이언트·서버 양쪽에서 하되, 클라이언트 검증은 즉각적 피드백용이고
**서버 검증이 실효적 방어**다.

## 9. 검증

이 저장소에는 테스트 러너가 없다. 검증은 실제 실행으로 한다.

**`vite dev`는 `api/` 폴더를 실행하지 않는다.** 로컬 전체 검증에는 `vercel dev`가
필요하므로 **Vercel CLI를 설치한다** (`npm i -g vercel`).

확인 항목:

1. `npm run build` (tsc -b + vite build) 통과
2. `vercel dev` — `k` 없이 접속 → 폼이 없고 목록만 보인다
3. `vercel dev` — `?k=<올바른 키>` → 폼이 열리고 제출 시 목록에 반영된다
4. `vercel dev` — 잘못된 키로 직접 POST → `403`
5. `vercel dev` — 메시지에 전화번호/이메일 → `400 PII_DETECTED`, 저장 안 됨
6. 프리뷰 배포 — **`vercel.json`의 `/(.*)` → `/index.html` 리라이트가
   `/api/guestbook`을 삼키지 않는지 확인.** Vercel은 리라이트보다 파일시스템·함수를
   먼저 매칭하므로 정상 동작이 유력하나, 배포 전에는 확정할 수 없다. 삼킨다면
   `/api`를 제외하는 규칙을 추가한다.
7. 프리뷰 배포 — 실제 휴대폰에서 QR 스캔 → 제출까지 완주

npm 설치 시 `--legacy-peer-deps`가 필요하다 (기존 `@tokens-studio/sd-transforms`가
`style-dictionary@^5`를 요구하나 저장소는 `4.4.0`).

## 10. 롤백 절차 (학회 종료 후)

1. `api/guestbook.ts` 삭제
2. `src/guestbook/` 폴더 삭제
3. `src/App.tsx`에서 import 1줄 + Route 1줄 제거
4. Vercel 환경변수 `GUESTBOOK_WRITE_KEY`, `GUESTBOOK_EXPIRES_AT` 삭제
5. Vercel Marketplace에서 Upstash 인테그레이션 제거
6. 재배포

데이터는 `GUESTBOOK_EXPIRES_AT` 시각에 자동 소멸하므로 **별도 삭제 작업이 없다.**
5번을 먼저 수행해도 무방하다.
